# Fenced Control API Helm chart

This chart deploys the production Control API over HTTPS. It requires existing
PostgreSQL and security Secrets; rendering with the default values fails until
the production configuration is supplied. Static development tenants cannot be
used with this chart because the development API only accepts loopback listeners.

The chart creates a Deployment, a Service, and optionally a ServiceAccount. It
does not install PostgreSQL, NATS, controllers, runtime workers, an ingress, or
database migrations. Provision those components separately for a complete
Fenced installation. The container image must include `/bin/fenced-control`.

## Prepare dependencies

All referenced Secrets must exist in the release namespace. Manage secret values
through your normal secret provisioning process, rather than putting them in
Helm values or command-line flags.

| Configuration | Required Secret content |
| --- | --- |
| `database.existingSecret` | `database-url`: PostgreSQL connection URL with the production database credentials and appropriate TLS settings |
| `security.tls.existingSecret` | `tls.crt`: PEM certificate chain; `tls.key`: matching PEM private key (a Kubernetes TLS Secret works) |
| `security.audit.existingSecret` | `audit-signing-key`: base64-raw encoded Ed25519 private key accepted by `fenced-control` |
| `security.packageTrust.existingSecret` | `package-trust-keys`: comma-separated `keyID=base64rawpub` Ed25519 package trust keys; at least one key is required |
| `embedding.tokenSecret` (optional) | `token`: bearer token for the embedding service |

The key names can be overridden with the corresponding `secretKey`,
`certificateKey`, `privateKeyKey`, `keysKey`, or `tokenSecretKey` values. Secrets
are referenced, never generated by this chart. TLS files are mounted read-only
at `/etc/fenced/tls/tls.crt` and `/etc/fenced/tls/tls.key`; probes use HTTPS.

Apply `db/migrations` to PostgreSQL before installing the chart. The database
needs the extensions required by those migrations, including pgvector. From the
repository checkout, with `DATABASE_URL` supplied securely in the environment:

```sh
go run ./cmd/fenced-migrate -directory db/migrations
```

The pods must be able to reach PostgreSQL, the HTTPS OIDC issuer's discovery/JWKS
endpoints, and the HTTPS embedding service. OIDC bearer **ID tokens** must have
the configured client audience and a non-empty tenant claim (default `tenant`).
The API verifies TLS using the container's trust roots for outbound connections;
provision suitable trust roots in the image if these endpoints use a private CA.

## Configure and install

Create a deployment values file with the names of your existing resources and
your actual endpoints. This example describes the required shape; its resource
names and `.example.com` endpoints must be replaced before installation:

```yaml
database:
  existingSecret: fenced-database
security:
  oidc:
    issuer: https://identity.example.com
    clientID: fenced-control
    tenantClaim: tenant
  tls:
    existingSecret: fenced-control-tls
  audit:
    existingSecret: fenced-audit-signing
    keyID: control-plane-audit
  packageTrust:
    existingSecret: fenced-package-trust
embedding:
  endpoint: https://embedding.example.com/embed
  tokenSecret: fenced-embedding-auth # omit for a keyless service
```

From the repository root:

```sh
helm lint deploy/helm/fenced --strict -f production-values.yaml
helm template fenced deploy/helm/fenced --namespace fenced -f production-values.yaml
helm upgrade --install fenced deploy/helm/fenced --namespace fenced -f production-values.yaml
```

Create the namespace and Secrets before the last command. Template validation
checks configuration, not whether the external resources, credentials, image,
or endpoints exist. Kubernetes and the API validate those at startup.

By default, the ServiceAccount has a release-specific name and does not mount a
Kubernetes API token; no RBAC permissions are granted. To use an existing
ServiceAccount, set `serviceAccount.create: false` and `serviceAccount.name`.

The earlier skeleton chart's `security.devTenant`, `postgresql`, `nats`,
`controller`, and `ingress` values are rejected by the values schema. Migrate
to the external dependencies above. If the earlier chart already created a
Deployment, recreate that Deployment during a planned upgrade: the selectors
now include the release identity, and Kubernetes Deployment selectors are
immutable. Separate releases in one namespace no longer share Service selectors.

## Upgrading the control plane without downtime

The chart upgrades the control plane the same way the kernel rolls a service:
the new replica joins and becomes ready before the old one leaves.

| Value | Default | Meaning |
| :--- | :--- | :--- |
| `upgrade.maxUnavailable` | 0 | The old replica is only taken away when the new one serves |
| `upgrade.maxSurge` | 1 | The new replica joins before the old one leaves |
| `upgrade.minReadySeconds` | 10 | A replica counts as available only after it stayed ready |
| `upgrade.progressDeadlineSeconds` | 600 | The rollout fails instead of waiting forever |
| `upgrade.terminationGracePeriodSeconds` | 30 | The replica may finish its work; the control plane drains on SIGTERM |
| `upgrade.podDisruptionBudget.enabled` | true | A voluntary disruption may not take the last replica down |
| `upgrade.podDisruptionBudget.minAvailable` | 1 | The number of replicas that survive a node drain |
| `upgrade.preStopSleepSeconds` | 0 | Optional delay between the removal from the Service and the SIGTERM; needs the Sleep lifecycle handler (Kubernetes 1.29 or newer) |

The schema of the control plane is migrated forward before the new replica
starts. Migrations are forward-only and additive, so the old replica keeps
working against the new schema.

The rollout of an *agent* version is a different operation and lives in the
Control API: see `docs/operations/rolling-upgrade.md`.

## Render verification

The render checks require Helm and Python with PyYAML. They never access a
cluster or create credentials:

```sh
python deploy/helm/fenced/tests/render_test.py
```

If Helm is outside `PATH`, set `HELM` to the executable path. The checks cover
missing production configuration, HTTPS startup/probes, Secret references and
TLS mounts, release isolation, ServiceAccount creation/reuse, optional embedding
authentication, rejected legacy settings, and linting the configured chart.
