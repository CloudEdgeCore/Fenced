# Fenced v1.2 Formal Public Contract Freeze

This document formalizes the **v1.2 Contract Freeze** for the Fenced Kernel and its standard communication protocols. All definitions in this specification, along with their matching Protobuf definitions under `proto/fenced/`, are frozen against breaking changes.

---

## 1. Specification Freeze Scope & Compatibility Guarantee

The following core public interfaces are officially frozen:

| Subsystem | Frozen Version | Protobuf Definition | Go Package / Rust ABI |
| :--- | :--- | :--- | :--- |
| **IPC Subsystem** | `v1` | `proto/fenced/ipc/v1/ipc.proto` | `fenced/ipc/v1;ipcv1` |
| **Agent Service & Supervisor** | `v1` | `proto/fenced/service/v1/service.proto` | `fenced/service/v1;servicev1` |
| **Syscall ABI** | `1.0.0` | `proto/fenced/syscall/v1/syscall.proto` | `fenced/syscall/v1;syscallv1` |
| **External Effect API** | `v1` | `proto/fenced/effect/v1/effect.proto` | `fenced/effect/v1;effectv1` |

### Backwards Compatibility Invariants
1. **Field Number Freeze**: No existing protobuf field tag numbers or enum ordinal values may be re-assigned or altered.
2. **Monotonic Semantics**: Fencing tokens, resource versions, and event cursors are strictly monotonically increasing.
3. **Additive-Only Evolution**: Minor version releases (`1.x`) may only introduce optional additive fields or new syscall numbers. Deprecated fields will remain reserved.
4. **Wire Format Agnostic**: Standard wire serializations are Protocol Buffers v3 and JSON Schema equivalent.

## 2. IPC Subsystem Contract (`fenced.ipc.v1`)

The IPC Subsystem provides durable, asynchronous, cross-agent mailbox messaging.

### 2.1 Addressing & Mailbox Binding
- **Target Address**: `AgentAddress` consists of `agent_version_ref` (`[namespace/]name@version`) and `instance` (the target run ID).
- **Run Survivability**: Mailboxes are tied to the logical run lifecycle. If an execution attempt crashes, pending mailbox messages remain unconsumed until the replacement attempt assumes the lease.

### 2.2 Wire Interface (`IPCGatewayService`)
- `SendMessage(SendMessageRequest) -> SendMessageResponse`
  - Enqueues a durable message with tenant boundary checks.
  - Requires `AttemptIdentity` with valid active fencing token.
  - Replays idempotently if `idempotency_key` matches.
- `ReceiveMessages(ReceiveMessagesRequest) -> ReceiveMessagesResponse`
  - Drains unacknowledged messages up to `max_messages` within `wait_millis`.
  - Increments `delivery_attempt` counter.
- `AcknowledgeMessage(AcknowledgeMessageRequest) -> AcknowledgeMessageResponse`
  - Confirms message receipt. Receiver deduplication guarantees at-least-once delivery with exactly-once application.

## 3. AgentService & Supervisor Lifecycle Contract (`fenced.service.v1`)

AgentService governs long-running, daemonized, and supervised multi-agent services.

### 3.1 Lifecycle States

```
                +-------------------------------------------------+
                |                                                 |
                v                                                 |
 [PENDING] --------> [ACTIVE] <---------> [DEGRADED]              | (Rollback)
                        |                      |                  |
                        +----------> [DRAINING] ------------------+
                                        |
                                        v
                                   [TERMINATED]
```

#### Service Phases (`ServicePhase`)
- `SERVICE_PHASE_PENDING (1)`: Spec accepted; instances not yet scheduled.
- `SERVICE_PHASE_ACTIVE (2)`: Desired replicas meet min_ready criteria with healthy heartbeats.
- `SERVICE_PHASE_DEGRADED (3)`: One or more instances failing, crashing, or missed heartbeats.
- `SERVICE_PHASE_DRAINING (4)`: Gracefully draining traffic and active tasks before termination or version replacement.
- `SERVICE_PHASE_TERMINATED (5)`: All instances terminated and resources released.

#### Instance Phases (`InstancePhase`)
- `INSTANCE_PHASE_STARTING (1)`: Process or container spawned.
- `INSTANCE_PHASE_RUNNING (2)`: Sending heartbeats within TTL; capable of accepting work.
- `INSTANCE_PHASE_DRAINING (3)`: Finishing in-flight tasks; rejecting new claims.
- `INSTANCE_PHASE_STOPPED (4)`: Clean exit (code 0).
- `INSTANCE_PHASE_FAILED (5)`: Non-zero exit or killed after heartbeat timeout.

### 3.2 Rollout & Self-Healing Guarantees
- **Surge & Availability Constraints**: Respects `max_surge` and `max_unavailable` during rolling upgrades.
- **Heartbeat & Deadlock Auto-Reap**: When `last_heartbeat_at + heartbeat_ttl < now()`, the supervisor fences the stale instance and provisions a replacement.

### 4.2 Error Code Mapping (`SyscallErrorCode`)

```
0:  SYSCALL_OK        - Successful completion
1:  SYSCALL_EPERM     - Operation not permitted (capability denied / tenant mismatch)
2:  SYSCALL_ENOENT    - No such entity, resource, or tool
3:  SYSCALL_EINVAL    - Invalid argument or malformed payload
4:  SYSCALL_EBUSY     - Resource locked or concurrent conflicting attempt
5:  SYSCALL_ETIMEDOUT - Deadline exceeded
6:  SYSCALL_ENOMEM    - Token quota or financial budget exhausted
7:  SYSCALL_EFENCE    - Stale fencing token or expired attempt lease
8:  SYSCALL_ENOSYS    - Syscall not implemented
9:  SYSCALL_EINTERNAL - Unhandled internal kernel fault
10: SYSCALL_EUNKNOWN  - Ambiguous external effect outcome (AUTO-REPLAY FORBIDDEN)
```

## 5. External Effect API Contract (`fenced.effect.v1`)

The Effect Subsystem isolates non-deterministic and irreversible external side-effects (e.g. payment gateway charges, external webhooks, email dispatch).

### 5.1 Monotonic Lease Fencing
- Every effect request must pass an `AttemptIdentity` with a `fencing_token`.
- If an agent attempt is evicted, restarted, or rescheduled, its lease token increases monotonically.
- The kernel rejects any effect invocation containing a fencing token less than the highest recorded token for that run with `SYSCALL_EFENCE`.

### 5.2 Idempotency & SHA-256 Verification
- Requests require a non-empty `idempotency_key`.
- The kernel computes `sha256(payload)`. If a request arrives with an existing key but differing payload, it is rejected with `SYSCALL_EINVAL`.
- Replaying a previously `COMMITTED` effect immediately returns the stored `EffectReceipt` with `replayed = true` without external dispatch.

### 5.3 The `UNKNOWN` State Non-Replay Guarantee
- If an external call times out, drops connection, or returns an ambiguous status, the effect enters `EFFECT_STATUS_UNKNOWN` (`SYSCALL_EUNKNOWN`).
- **CRITICAL INVARIANT**: The kernel and runtimes are forbidden from auto-retrying or blindly replaying an `UNKNOWN` effect. Manual resolution or compensations must be triggered.
