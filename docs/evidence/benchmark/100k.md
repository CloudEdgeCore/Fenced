## 4. 验收

### 正确性 — 全部通过 ✅

```text
Lost Tasks = 0                    ✅ (3/3 runs, exactness 断言全过)
Duplicate Final Execution = 0     ✅
Deadlock = 0                      ✅
Panic = 0                         ✅
Permanent Stuck Task = 0          ✅
```

### 稳定性 — 共享 CI 硬件上不达标 ❌

```text
吞吐差异:  35.1% (27.2 / 21.0 / 20.2 tasks/s)   要求 <= 10% ❌
P95 差异:  37.7% (58m32s / 1h16m54s / 1h20m34s) 要求 <= 15% ❌
```

**根因**：GitHub hosted runner 每次运行分配到不同的共享 VM。三次运行代码、
配置完全相同，但 schedule 阶段耗时 28m47s / 43m50s / 47m24s——近 1.7 倍差距，
是宿主机性能差异（noisy neighbor），不是系统行为差异。
（Run #1 恰好分到较快 runner，#2/#3 较慢且相互接近：21.0 vs 20.2 = 4%。）

## 5. 结论

1. **正确性证据（核心目标）已成立**：100K 任务全管线 3/3 通过，零丢失、零重复、
   零卡死——"在高负载下保持正确"的主张有了 100K 规模的可审计证据。
2. **性能稳定性无法在共享 CI 硬件上认证**：≤10% 的稳定性标准隐含"同一台机器"
   前提。formal 稳定性认证需要固定硬件（建议复用 soak 自托管 runner，
   同机连续跑 3 次后再出正式性能基线）。
3. 修复记录：本基线过程中发现并修复了 scheduler lease TTL 硬编码 30 分钟
   不足以覆盖 100K 管线（77 分钟）的 pre-existing bug（PR #53，
   修复前 nightly 已连挂 9 次）。
