## 1. Why this document exists

Every other scale claim in this repository stops at 100K. `README.md` recorded the 1M
baseline as **Not produced**: the `capacity-baseline-1m` nightly job is gated behind a
self-hosted runner pool that has never been provisioned, and three local attempts on
2026-09-12 died at 257K / 48K / 475K of 1M before host-side termination. No 1M run had
ever completed on any machine.

`baseline.md` §2 defines 1M as scenario C and §5 requires three consecutive runs on one
environment inside ≤10% throughput / ≤15% P95 spread. This document is that measurement.

It is also the first capacity number in this repository produced on hardware that meets
the §1 recommended specification — 8 vCPU / 32 GB / NVMe, the floor below which
`baseline.md` says results must not be compared across versions.

## 3. Procedure

A driver ran the test three times sequentially, back to back, against the same PostgreSQL
instance, without restarting the database or the container between runs:

```bash
export FENCED_CAPACITY_TASKS=1000000
export FENCED_TEST_DATABASE_URL='postgres://fenced:...@127.0.0.1:5432/fenced?sslmode=disable'
/usr/local/go/bin/go test -tags=integration -count=1 -timeout 2880m \
  -run '^TestControlPlanePipelineCapacityBaseline$' -v \
  ./internal/kernel/store/postgres/
```

Each run builds its own `fenced_capacity` schema and truncates its own kernel tables, so
the runs are independent of one another and cannot touch a business database. Compilation
was warmed with a compile-only pass before run 1 so the compile step is not billed into the
first measured run.

The test asserts correctness only — it does not look at wall-clock time — so a `PASS` is
not by itself evidence of stability; the spreads below are computed from the `CAPACITY
REPORT` lines it prints.

Spread is defined as `max/min - 1`, the same definition used in the 100K stability
document.

### 3.1 Deviation from the planned procedure — recorded, not smoothed over

**The `-timeout` was raised from `1080m` to `2880m` before this batch, and the change was
not justified by the evidence.** Reasoning at the time: the admission phase was observed
stepping at ~62.7 tasks/s at one instant, which extrapolated to ~20 h total; 18 h
(`1080m`) would therefore not fit. That extrapolation was wrong. The admission phase
actually averaged 85 tasks/s across the whole phase — a single instantaneous sample
understated it by ~35% — and the schedule/admit ratio at 1M is 1.6x, not the 2.85x seen at
100K. Real per-run duration turned out to be ~9.2 h, so `1080m` would have been sufficient
with large margin. The higher timeout therefore did not buy anything; its only cost was the
aborted first attempt below.

**A first attempt was aborted 24 minutes in.** Before restarting with the raised timeout,
the driver had been running since `2026-09-16T04:59:25Z` and had reached 54,950 / 1,000,000
tasks in the admission phase when it was killed to apply the timeout change. Its logs are
retained on the host as `abort1-1m-v110-*` but are **not published here** — they contain no
completed run and no certified number. The published batch starts at
`2026-09-16T05:24:03Z`.

The test's exactness block asserts, per run, that all 1,000,000 tasks reached `SUCCEEDED`,

### 5.4 Where the time goes, and what the bottleneck is

The end-to-end pipeline is dominated by two phases. At 1M the schedule phase alone is
5h14m–5h31m and admission is 3h10m–3h17m; together they account for ~93% of wall clock.
Completion is comparatively cheap (28m43s–29m15s at 574–581 tasks/s). Per-task end-to-end
latency is ~9 h, which follows directly: with a strictly serial controller draining 1M
tasks it is arithmetically impossible for the last task to finish sooner than the sum of
the phases.

The binding constraint is **single-core PostgreSQL**, not disk and not memory:

```text

                       multi-core bursts
```

## 6. What this certifies — and what it does not

**Certified:** on one fixed host meeting `baseline.md` §1, at source commit `45598a9`, three
consecutive 1M-task pipeline runs varied by 3.45% in end-to-end throughput and 2.95% in P95
latency, inside the ≤10% / ≤15% targets, with zero lost, duplicated, or stuck tasks. The
previously empty scenario C in `baseline.md` now has a measured entry.

**Not certified by this document:**

- **A production capacity number.** ~30 tasks/s end to end is what one m7i.2xlarge with a
  containerised PostgreSQL on the same host produced under a deliberately untuned 2 GiB
  `shared_buffers` and a single admission controller and scheduler. It is not a throughput
  figure for supported production hardware or for a tuned deployment, and it should not be
  read as an upper bound — the per-phase numbers show the serial controller drain, not a
  hardware ceiling, is what sets the wall clock.
- **Stability on other hardware or at other scales.** One host, one configuration, one
  scale. The 100K stability result in `100k-stability-2026-09-15.md` is a separate
  measurement on a different host and is not a second data point for this one.
- **Absence of scaling degradation between 100K and 1M.** Not measured here. The two runs
  differ in host, OS, and disk as well as in scale, so subtracting them would not isolate
  scale. A same-host 100K → 1M comparison was not run.
- **The 24h / 72h / 7d soaks.** Still unproduced — see `README.md` Current boundaries.
- **Anything about preemption**, which remains deliberately unimplemented and is documented
  as such in the README.

### 6.1 The disk result needs its own caveat

Disc utilisation peaked at **98.70%** with **126.16 MiB/s** of writes, which is exactly the
gp3 baseline of 125 MiB/s. That is a genuine saturation event and it did not occur at 100K,
where disk utilisation on the workstation run stayed near 4.9%.

It is recorded as a **burst, not a sustained bottleneck**: of 1637 samples, only 82 (5.01%)
were at or above 80% utilisation, and only 28 (1.71%) at or above 95%. 94.56% of samples
were below 20%. The pattern is consistent with checkpoint and WAL flush spikes (the run ends
with `max_wal_size` reached, ~8.2–9.6 GB of WAL) rather than continuous back-pressure, and
the fact that throughput stayed inside 3.45% across three runs while the bursts recurred
argues against the disk being the term that sets run-to-run variance. The dominant
constraint remains the saturated PostgreSQL core. But this is an inference from utilisation
samples, not a controlled experiment: **no run was performed with a faster or larger volume,
so the claim "gp3 is not the bottleneck at 1M" is not established here.**

## 7. Reproducing

The driver and sampler used for this batch are published alongside the logs. On a host with
Go 1.26.6, Docker, and a PostgreSQL 18 reachable over loopback:

```bash
# 1. pin the tree and prove it is the commit you think it is
git -C ~/fenced fetch --all
git -C ~/fenced checkout 45598a9c09782529359f550446a9f7ff554f8d21
git -C ~/fenced status --porcelain    # must be empty

# 2. start PostgreSQL with the §2 configuration, then:
mkdir -p ~/bin ~/capacity-runs
cp run-capacity.py db-sampler.sh ~/bin/ && chmod +x ~/bin/*

# 3. drive three runs (~28 h)
python3 ~/bin/run-capacity.py 1000000 3 1m-v110 \
  'postgres://fenced:...@127.0.0.1:5432/fenced?sslmode=disable' 2880m
```

`run-capacity.py` rewrites `<prefix>.status` after every state change and appends to
`<prefix>-driver.log`, so a killed driver still leaves a truthful record of where it
stopped. It also warms the compiler once before run 1 and samples host memory, swap,
container RSS, connection counts and disk utilisation every 60 s into
`<prefix>-samples.log`.

### 8.1 Note on the two database-sampling files

`1m-v110-dbsamples.frozen.log` is the sampler output as frozen when the sampler was stopped
on 2026-09-18, after the batch had already finished. Because the sampler was not tied to the
driver's lifetime, it kept appending idle-database rows for ~21 h past the end of run 3
(2951 lines total, of which 1287 are post-run idle samples).

`1m-v110-dbsamples.run.log` is the same file truncated at `2026-09-17T09:10:20Z` — the
timestamp of the batch's terminal `SUCCESS` line — so that it covers exactly the three
measured runs and nothing else (1664 lines). All database statistics in §5.4 are taken from
this run-scoped file. Both are published so the truncation is auditable rather than silent.
