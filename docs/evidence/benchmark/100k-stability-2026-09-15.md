## 1. Why this document exists

[`100k.md`](100k.md) records the 100K-scale pipeline as **correct** on 3/3 runs but **not
certifiable for stability**: the targets (end-to-end throughput spread ≤10%, P95 spread ≤15%)
implicitly assume one machine, and the three CI runs were scheduled onto different shared
VMs, producing a 35.1% / 37.7% spread that `100k.md` attributes to host variance rather than
system behaviour. `100k.md` §5 therefore asks for the same three runs back to back on fixed
hardware.

This document is that measurement. One host, one source tree, one binary, three consecutive
runs.

## 3. Procedure

A driver ran the test three times sequentially, back to back, against the same PostgreSQL
instance, without restarting the database between runs:

```powershell
go test -tags=integration -count=1 -timeout 360m `
        -run '^TestControlPlanePipelineCapacityBaseline$' -v `
        ./internal/kernel/store/postgres/
# env: FENCED_CAPACITY_TASKS=100000
#      FENCED_TEST_DATABASE_URL=postgres://fenced:...@127.0.0.1:15432/fenced
```

Each run builds its own `fenced_capacity` schema and truncates its own kernel tables, so the
runs are independent of one another and cannot touch a business database. The test asserts
correctness only — it does not look at wall-clock time — so a `PASS` is not by itself evidence
of stability; the spreads below are computed from the `CAPACITY REPORT` lines it prints.

Spread is defined as `max/min - 1`, the same definition that reproduces the 35.1% / 37.7%
figures in `100k.md` from the CI runs (27.2 / 21.0 / 20.2 tasks/s and 3512 / 4614 / 4834 s).

### 5.3 Per-phase throughput — one sub-phase does not meet the 10% figure

```text
enqueue  : 12.82%  (397 / 440 / 390 tasks/s)   <-- above 10%
complete :  8.33%  (143 / 132 / 140 tasks/s)
schedule :  4.55%  ( 89 /  92 /  88 tasks/s)
admit    :  4.42%  (232 / 236 / 226 tasks/s)
```

The `enqueue` sub-phase spread is 12.82%, above the 10% figure the targets are expressed in,
even though the end-to-end metric that the target is defined on met it. The `enqueue` phase is
a short burst (3m47s–4m16s out of a ~42 min run) that runs concurrently with the admission
controller, so it absorbs background scheduling jitter from the host; the variance is not
compensated elsewhere in the pipeline — the total wall-clock spread stays at 2.08%. This is
recorded rather than smoothed over: the certified metrics are end-to-end throughput and P95
spread; no claim is made that every sub-phase stays inside 10%.

## 6. What this certifies — and what it does not

**Certified:** on one fixed host and one source commit, three consecutive 100K-task pipeline
runs varied by 2.56% in end-to-end throughput and 1.78% in P95 latency, inside the ≤10% / ≤15%
targets. The stability targets are reachable and the previously observed 35% / 38% spread is
explained by host variance, not by the kernel's behaviour.

**Not certified by this document:**

- **A production capacity number.** ~40 tasks/s end to end is what one developer workstation
  with a containerised PostgreSQL and 15 unrelated containers competing for the same CPU
  produced. It is not a throughput figure for supported hardware, and it is not comparable to
  the Linux CI numbers in `100k.md` (different OS, different PostgreSQL configuration, notably
  `synchronous_commit=off` here).
- **Stability on other hardware or under other load.** The measurement is one host, one
  configuration. The targets assume fixed hardware; this run shows they are met on *this*
  fixed hardware.
- **The 24h / 72h / 7d soaks and the 1M-scale baseline.** Those remain unproduced — see
  `README.md` Feature status and Current boundaries.
- **Anything about preemption**, which remains deliberately unimplemented and is documented as
  such in the README.
